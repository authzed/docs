# DownloadPermissionSets

For large datasets, `DownloadPermissionSets` is a faster alternative to [LookupPermissionSets] for the initial [backfill](../concepts/permission-set-lifecycle): instead of streaming individual events over a single connection, it hands you a manifest of files you can fetch directly from blob storage, in parallel.

## Request

The request maps to [`DownloadPermissionSetsRequest`]:

```json
{
  "optional_at_revision": "the_zed_token"
}
```

If `optional_at_revision` is omitted, Materialize returns files for the latest fully-published revision. If provided, Materialize returns files for that specific revision if they're still available (see [Snapshot rotation](../concepts/snapshots#snapshot-lifecycle-events)).

Once you've backfilled from the downloaded files, switch to [WatchPermissionSets] to keep your copy current. See [The Permission Set Lifecycle](../concepts/permission-set-lifecycle) for the full flow.

## Response

The response ([`DownloadPermissionSetsResponse`]) lists the available [`File`]s:

```json
{
  "timestamp": "2024-05-10T11:10:38Z",
  "at_revision": {
    "token": "GiAKHjE3MTUzMzk0Mzg2MjA4NzI1MDIuMDAwMDAwMDAwMA=="
  },
  "files": [
    { "name": "metadata.json", "url": "https://..." },
    { "name": "flat_member_to_set.parquet", "url": "https://..." },
    { "name": "flat_set_to_set.parquet", "url": "https://..." }
  ]
}
```

`at_revision` is the ZedToken for the revision the files were built at. When you switch to [WatchPermissionSets] after the backfill, pass it as `optional_starting_after` so the stream picks up right after the files, without gaps.

Each file's `url` is a **time-limited signed URL**: download promptly, and re-call `DownloadPermissionSets` to get fresh URLs if a batch download runs long. `metadata.json` is always included and describes the revision:

```json
{
  "revision": "1715339438620872502.0000000000",
  "watched_permissions": ["document#view@user", "document#edit@user"],
  "numShards": 4,
  "files": ["flat_member_to_set-shard-0.parquet", "flat_member_to_set-shard-1.parquet", "..."]
}
```

`revision` is in the datastore's own revision format. Where an API needs a ZedToken for this revision, use the response's `at_revision`.

<Callout type="warning">
  Large datasets are sharded across multiple files per table (`flat_member_to_set-shard-0.parquet`,
  `flat_member_to_set-shard-1.parquet`, and so on). Read `metadata.json`'s `files` list to discover
  the actual shard files for a revision, and treat each table's shards as one combined multi-file
  dataset.
</Callout>

## Files

Materialize publishes [permission set](../concepts/permission-sets) data as two Parquet files, one for each kind of edge. Every row holds the full string values for both ends of its edge, so you don't need lookup tables to read them.

### `flat_member_to_set.parquet`

Each row is a **member → set** edge: a subject that's directly a member of a set. Subjects are usually members of the relation they were written to, such as `document:123#viewer`, rather than of the permission you watch, such as `document:123#view`. The relation's set is then nested in the permission's set, in `flat_set_to_set.parquet`.

| Column          | Example    | Meaning                                                    |
| --------------- | ---------- | ---------------------------------------------------------- |
| `resource_type` | `document` | The set's resource type                                    |
| `resource_id`   | `123`      | The set's resource ID                                      |
| `resource_rel`  | `viewer`   | The set's relation or permission                           |
| `subject_type`  | `user`     | The member's type                                          |
| `subject_id`    | `evan`     | The member's ID                                            |
| `subject_rel`   |            | The member's relation, or empty if the member is an object |

### `flat_set_to_set.parquet`

Each row is a **set → set** edge: a **child** set nested in a **parent** set, so every member of the child is also a member of the parent. Nesting is already flattened: a set nested several levels deep links straight to the permission it grants. See [Permission Sets](../concepts/permission-sets) for what "child" and "parent" mean here.

| Column                 | Example       | Meaning                                 |
| ---------------------- | ------------- | --------------------------------------- |
| `child_resource_type`  | `group`       | The child set's resource type           |
| `child_resource_id`    | `engineering` | The child set's resource ID             |
| `child_resource_rel`   | `member`      | The child set's permission or relation  |
| `parent_resource_type` | `document`    | The parent set's resource type          |
| `parent_resource_id`   | `456`         | The parent set's resource ID            |
| `parent_resource_rel`  | `view`        | The parent set's permission or relation |

### Querying the files

These are plain Parquet files, so any Parquet reader works: DuckDB, pandas/pyarrow, Spark, and most data warehouses can query them directly without a custom parser.

To find everyone in a permission set, combine its direct members with the members of its child sets. Because nesting is already flattened, one join is enough. For example, with [DuckDB](https://duckdb.org/):

```sql
-- Every subject that can view document 123
SELECT subject_type, subject_id
FROM 'flat_member_to_set.parquet'
WHERE resource_type = 'document' AND resource_id = '123' AND resource_rel = 'view'
UNION
SELECT m.subject_type, m.subject_id
FROM 'flat_set_to_set.parquet' s
JOIN 'flat_member_to_set.parquet' m
  ON m.resource_type = s.child_resource_type
  AND m.resource_id = s.child_resource_id
  AND m.resource_rel = s.child_resource_rel
WHERE s.parent_resource_type = 'document'
  AND s.parent_resource_id = '123'
  AND s.parent_resource_rel = 'view';
```

See [Syncing to a Relational Database](../guides/relational-database) for the same pattern in tables you keep up to date.

## Errors

### NotFound

Returned when no download manifest exists for the requested revision (or for the latest revision, if none was specified). For example, if hydration hasn't published a manifest yet, or the requested revision has aged out. Retry against the latest revision, or re-run without `optional_at_revision`.
